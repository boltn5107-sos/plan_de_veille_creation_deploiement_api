IIntroduction générale aux API

Une API est un contrat qui permet à deux logiciels de communiquer sans connaître leurs implémentations respectives. C'est la brique de base de l'informatique moderne connectée.

1.1. Définition d'une API

Une API (Application Programming Interface, interface de programmation applicative) est un ensemble de règles, de types de données et de points d'entrée qui permet à un programme d'utiliser les fonctionnalités d'un autre programme. Elle définit ce que l'on peut demander et comment le demander, mais masque comment c'est réalisé à l'intérieur.

On peut la comparer au menu d'un restaurant : le menu décrit les plats disponibles et la manière de les commander ; il ne décrit ni la cuisine, ni le fournisseur, ni les recettes. Le client (l'application appelante) n'a pas besoin de connaître la cuisine (l'implémentation) pour être servi.

API locale / bibliothèque

Une classe ou un module que l'on importe dans son propre code (ex. json.dumps(), une bibliothèque de calcul). L'appel se fait en mémoire, dans le même processus.

API Web / distante

Une interface exposée sur le réseau via HTTP (ex. GET https://api.exemple.com/tasks). L'appel traverse le réseau et suit un contrat documenté (OpenAPI, par exemple).

1.2. Rôle et importance des API

  • Interopérabilité : faire dialoguer des technologies hétérogènes (Python, Java, JavaScript, mobile).
  • Découplage : les équipes évoluent indépendamment tant que le contrat est respecté.
  • Réutilisation : un service de paiement, d'authentification ou de géolocalisation est partagé par plusieurs produits.
  • Automatisation : les API permettent l'intégration continue, les workflows, les agents et les scripts.
  • Écosystème et monétisation : une API publique peut attirer des développeurs et générer des revenus (Stripe, Twilio, OpenWeather).
  • Scalabilité organisationnelle : les équipes communiquent par contrats plutôt que par réunions ; c'est la base des microservices.

IIClassification des API

Toutes les API ne se ressemblent pas : le style technique, la politique de publication et le contexte déterminent des choix très différents.

2.1. Les styles et technologies d'API Web

REST (Representational State Transfer)

Style architectural introduit par Roy Fielding en 2000. Il repose sur les ressources identifiées par des URIs, les méthodes HTTP et des représentations (souvent JSON). C'est le style dominant des API publiques.

Pourquoi : simplicité, compatibilité avec le Web, cache HTTP, outillage abondant.
Comment : ressources au pluriel (/tasks), verbes HTTP, codes de statut, HATEOAS optionnel.
Exemple : GET /api/v1/tasks/42 renvoie 200 et {"id":42,"title":"..."}.

SOAP (Simple Object Access Protocol)

Protocole basé sur XML, avec une enveloppe normalisée, un contrat WSDL et de nombreuses extensions (WS-Security, WS-Addressing). Très utilisé dans les systèmes bancaires et les SI d'entreprise.

Pourquoi : contrats stricts, sécurité et transactions normalisées, interopérabilité d'entreprise.
Comment : un seul endpoint, opérations décrites dans un WSDL, messages XML.
Exemple : POST /BankService avec une enveloppe <soap:Envelope> contenant <GetBalance>.

GraphQL

Langage de requête et runtime créé par Facebook (2015). Le client demande exactement les champs dont il a besoin, à travers un seul endpoint.

Pourquoi : éviter le sur-fetch et le sous-fetch, agréger plusieurs sources, typage fort du schéma.
Comment : schéma (type Query), requêtes query, mutations, resolvers.
Exemple : { task(id: 42) { title done } } renvoie uniquement les champs demandés.

gRPC

Framework RPC de Google basé sur HTTP/2 et Protocol Buffers, avec génération de code client/serveur et support du streaming bidirectionnel.

Pourquoi : performances élevées, contrat binaire compact, streaming, typage fort.
Comment : fichier .proto, génération de stubs, appels de méthodes distantes.
Exemple : rpc GetTask(TaskRequest) returns (TaskResponse).

Autres styles

  • JSON-RPC / XML-RPC : appels de procédures simples via HTTP, sans sémantique de ressources.
  • WebSocket : canal bidirectionnel persistant, adapté au temps réel (chat, jeux, cours boursiers).
  • SSE (Server-Sent Events) : flux unidirectionnel serveur → client, simple et compatible HTTP.
  • Webhooks : le serveur notifie le client via un appel HTTP sortant (événements).

2.3. Critères de choix d'une API

  • Besoins fonctionnels : CRUD simple, requêtes complexes, temps réel, streaming, événements.
  • Contraintes techniques : navigateur, mobile, réseau limité, latence, volume, taille des messages.
  • Sécurité : authentification, autorisation fine, conformité (RGPD, PCI-DSS).
  • Écosystème et compétences : langages, bibliothèques, outils de test, courbe d'apprentissage.
  • Cache et performance : cache HTTP, CDN, compression, pagination.
  • Documentation et support : OpenAPI, exemples, SDK, communauté.
  • Coût total : développement, exploitation, monitoring, licences.
  • Évolutivité : versioning, compatibilité ascendante, gouvernance.
Méthode de choix

Commencer par le besoin métier, puis éliminer les styles incompatibles avec les contraintes dures (navigateur, temps réel, sécurité), puis comparer les options restantes sur le coût et l'écosystème. Pour une API CRUD classique consommée par un front web, REST + JSON reste le choix par défaut le plus rationnel.

IIIArchitecture des applications et des API

L'architecture décrit la manière dont les composants d'un système sont organisés, communiquent et évoluent. Le choix conditionne la scalabilité, la résilience et l'organisation des équipes.

3.1. Architecture client-serveur

Le client (navigateur, mobile, script) envoie une requête ; le serveur traite et renvoie une réponse. C'est le modèle de base du Web et de toute API HTTP.

Exemple : une application React interroge une API FastAPI ; l'application mobile Android interroge la même API.

3.2. Architecture monolithique

Une application unique, déployée comme un seul artefact, contenant toutes les fonctionnalités (interface, logique métier, accès aux données).

  • Avantages : simplicité de développement et de déploiement, transactions ACID locales, débogage plus simple, coût initial faible.
  • Inconvénients : couplage fort, scaling global, déploiements risqués, difficulté à faire évoluer plusieurs équipes, dette technique.
  • Variante recommandée : le modular monolith (monolithe modulaire), avec des modules bien séparés et des frontières claires, qui prépare une éventuelle extraction en services.

Exemple : une application de gestion de tâches avec interface serveur, authentification, base de données et export PDF dans un seul projet FastAPI.

3.3. Architecture orientée services (SOA)

Des services métier autonomes et réutilisables communiquent via un bus d'intégration (ESB). Les services exposent des contrats (souvent SOAP/WSDL) et sont orchestrés.

  • Avantages : réutilisation, gouvernance centralisée, intégration de systèmes hétérogènes.
  • Inconvénients : ESB centralisé et coûteux, complexité, couplage via le bus, latence, lourdeur de gouvernance.
  • Exemple : un SI bancaire expose les services « Client », « Compte », « Paiement » via un ESB.

3.4. Architecture microservices

Un système composé de services petits, indépendamment déployables, organisés autour de contextes métier (bounded contexts du DDD), chacun avec ses données et son contrat d'API.

  • Avantages : déploiement indépendant, scaling ciblé, autonomie des équipes, choix technologique par service, isolation des pannes.
  • Inconvénients : complexité distribuée (réseau, latence, pannes partielles), cohérence des données (sagas), observabilité, coût opérationnel, gouvernance des contrats.
  • Patterns clés : API Gateway, service discovery, circuit breaker, bulkhead, saga, outbox, tracing distribué.

IVFonctionnement d'une API Web

Comprendre le trajet d'une requête, du clic jusqu'à la base de données et retour, est indispensable pour diagnostiquer les erreurs, optimiser les performances et sécuriser l'ensemble.

4.1. Principes de communication sur le Web

  • URI : identifie une ressource (https://api.exemple.com/v1/tasks/42).
  • DNS : traduit le nom de domaine en adresse IP.
  • TCP : transporte les octets de manière fiable, dans l'ordre.
  • TLS : chiffre la connexion (HTTPS) et authentifie le serveur via un certificat.
  • HTTP : protocole de requête/réponse, sans état entre deux requêtes.
  • Intermédiaires : proxies, API Gateway, load balancer, CDN, reverse proxy (Nginx, Traefik).
  • Stateless : chaque requête contient tout le contexte nécessaire (token, paramètres) ; l'état métier est stocké côté serveur (base, cache).

4.2. Processus d'appel d'une API

  1. Résolution DNS du nom de domaine.
  2. Ouverture TCP (handshake) puis négociation TLS (HTTPS).
  3. Envoi de la requête HTTP : méthode, chemin, en-têtes, corps éventuel.
  4. Routage par le serveur ou la passerelle vers le bon endpoint.
  5. Validation des paramètres, de l'authentification et des autorisations.
  6. Traitement métier et accès aux données (base, cache, services externes).
  7. Construction de la réponse : code, en-têtes, corps sérialisé (JSON).
  8. Transport retour, éventuel cache, puis traitement par le client.

4.5. Formats d'échange de données

JSON

Format texte léger, lisible, natif en JavaScript. Types de base : objet, tableau, chaîne, nombre, booléen, null. C'est le format par défaut des API REST modernes.

{
  "id": 43,
  "title": "Réviser HTTP",
  "tags": ["api", "rest"],
  "done": false,
  "due_date": "2026-11-05",
  "meta": null
}

Bonnes pratiques : dates ISO 8601 (2026-11-05T14:30:00Z), identifiants explicites, pas de nombres flottants pour l'argent (utiliser des entiers en centimes ou des chaînes décimales), pas de champs null inutiles, versionner le schéma.

XML

Format balisé, verbeux mais très structuré, utilisé par SOAP et certains SI. Il dispose de schémas XSD et de transformations XSLT.

<task id="43">
  <title>Réviser HTTP</title>
  <done>false</done>
  <dueDate>2026-11-05</dueDate>
</task>

Autres formats

  • application/x-www-form-urlencoded : formulaires HTML simples.
  • multipart/form-data : upload de fichiers + champs.
  • application/octet-stream : binaire brut (fichier, image).
  • Protocol Buffers : binaire compact pour gRPC.
  • CSV / Parquet : exports de données et analytics.
  • YAML : configuration, spécifications OpenAPI.
Négociation de contenu

Le client envoie Accept: application/json ; le serveur répond avec Content-Type: application/json. S'il ne peut pas produire ce format, il renvoie 406 Not Acceptable. FastAPI gère cela via les paramètres et les types de réponse.

VProtocole HTTP et méthodes de requête

HTTP est le langage commun du Web. Une API REST n'est rien d'autre qu'un ensemble de conventions solides posées sur HTTP.

5.1. Présentation du protocole HTTP

HTTP (HyperText Transfer Protocol) est un protocole de communication client-serveur, textuel dans sa version 1.1, sans état, où chaque échange est une requête suivie d'une réponse. Il est normalisé par l'IETF (RFC 9110 pour la sémantique).

VersionTransportApports principaux
HTTP/1.0TCPUne connexion par requête, en-têtes simples.
HTTP/1.1TCPConnexions persistantes (keep-alive), pipelining, cache, Host obligatoire.
HTTP/2TCP + TLS (en pratique)Multiplexage des flux, compression des en-têtes (HPACK), priorisation, binaire.
HTTP/3QUIC / UDPRéduction de la latence, reprise rapide, meilleure résistance aux pertes.

Sans état : le serveur ne mémorise pas automatiquement le contexte entre deux requêtes. L'authentification et les préférences sont donc transmises à chaque appel (token, cookies, paramètres), et l'état métier vit dans une base ou un cache.

5.2. Les méthodes HTTP

Les méthodes indiquent l'intention de la requête. Elles portent une sémantique normalisée : sûre (pas de modification) et idempotente (le même appel répété produit le même effet).

Idempotence : pourquoi c'est essentiel

Un client peut réessayer une requête après un timeout réseau. Si l'opération est idempotente, un second appel ne crée pas de doublon et ne produit pas d'effet supplémentaire. POST n'étant pas idempotent, on utilise souvent une clé d'idempotence : le serveur mémorise la clé et renvoie la même réponse si la requête est rejouée.

Exemple : PUT vs PATCH

PUT /tasks/42 avec {"title":"A","done":true} remplace toute la ressource : les champs omis sont réinitialisés ou rejetés. PATCH /tasks/42 avec {"done":true} ne modifie que le champ done. Choisir PUT pour une réécriture complète, PATCH pour une mise à jour ciblée.

Pièges fréquents
  • Utiliser GET pour modifier des données (non sûr, cache et robots peuvent le déclencher).
  • Mettre un corps dans GET : non standard, ignoré par certains proxies.
  • Utiliser POST /tasks/42/delete au lieu de DELETE /tasks/42.
  • Utiliser PUT avec un corps partiel : ce n'est pas la sémantique de PUT.

VICodes de statut HTTP

Le code de statut est le premier contrat de lecture d'une réponse : il indique si l'appel a réussi, échoué côté client ou côté serveur, et oriente la stratégie de retry.

6.1. Présentation des codes de statut

Un code est un nombre à trois chiffres : le premier chiffre indique la catégorie, les deux suivants précisent le cas. Le client doit toujours vérifier le code avant de lire le corps de la réponse.

6.2. Les cinq catégories de codes HTTP

6.4. Gestion des erreurs dans les API

Une API professionnelle renvoie des erreurs cohérentes, documentées et exploitables par le client. Le standard recommandé est Problem Details (RFC 9457), avec le type MIME application/problem+json.

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.exemple.com/errors/validation",
  "title": "Échec de validation",
  "status": 422,
  "detail": "Le champ 'due_date' doit être une date future.",
  "instance": "/api/v1/tasks",
  "request_id": "9b2f7c1e",
  "errors": [
    {"field": "due_date", "message": "date passée", "code": "date_in_future"}
  ]
}

Bonnes pratiques :

  • Un format d'erreur unique pour toute l'API (mêmes champs, même structure).
  • Un code HTTP correct ; ne pas renvoyer 200 avec {"error": ...}.
  • Un message utile pour le développeur, sans divulguer de secrets, de stack traces ni de détails d'infrastructure.
  • Un identifiant de corrélation (request_id) présent dans les logs et la réponse.
  • Documenter les erreurs possibles dans OpenAPI, avec des exemples.
  • Retenter uniquement les erreurs transitoires (429, 502, 503, 504) avec un backoff exponentiel et un jitter.
Comment retenter intelligemment

Ne jamais retenter un 400, 401, 403, 404 ou 422 sans correction. Pour 429 et 5xx, respecter Retry-After, plafonner le nombre d'essais (3 à 5), et utiliser des clés d'idempotence pour les écritures.

VIIArchitecture REST

REST n'est pas un protocole ni une norme : c'est un style architectural défini par des contraintes. Les respecter produit des API prévisibles, cacheables et évolutives.

7.1. Définition et origine

REST (Representational State Transfer) a été formalisé par Roy Fielding dans sa thèse de doctorat en 2000. L'idée centrale : exposer des ressources identifiées par des URIs, que les clients manipulent à travers des représentations (JSON, XML...), en utilisant l'interface uniforme de HTTP.

Une API est dite RESTful lorsqu'elle respecte les contraintes ci-dessous. En pratique, beaucoup d'API dites « REST » sont en réalité « HTTP + JSON orientées ressources » et n'implémentent pas HATEOAS.

7.2. Les contraintes REST

ContrainteSignificationBénéfice
Client-serveurSéparation de l'interface et du stockage/traitement.Évolution indépendante des deux côtés.
Sans étatChaque requête contient tout le contexte nécessaire.Scalabilité, reprise après panne, simplicité.
CacheableLes réponses indiquent si elles peuvent être mises en cache.Réduction de la charge et de la latence.
Interface uniformeIdentification des ressources, manipulation par représentations, messages auto-descriptifs, HATEOAS.Prévisibilité, interopérabilité, découplage.
Système en couchesProxies, gateways, CDN, load balancers intercalés.Sécurité, scalabilité, résilience.
Code à la demande (optionnel)Le serveur peut envoyer du code exécutable (JS).Extensibilité du client.

7.3. Ressources, URIs et représentations

  • Ressource : un objet ou une collection métier (task, tasks, users).
  • URI : un nom de ressource, pas une action. On écrit /tasks, pas /getTasks.
  • Représentation : la forme transmise à un instant donné (JSON), distincte de la ressource elle-même.
  • Nommage : noms au pluriel, en minuscules, séparés par des tirets (/task-lists), pas de verbes.
  • Hiérarchie : /users/42/tasks pour les tâches d'un utilisateur ; éviter les imbrications profondes (2 niveaux maximum).

7.4. HATEOAS et maturité de Richardson

HATEOAS (Hypermedia As The Engine Of Application State) consiste à inclure dans la réponse les liens vers les actions possibles. Le client découvre les transitions au lieu de coder des URLs en dur.

{
  "id": 42,
  "title": "Réviser REST",
  "done": false,
  "_links": {
    "self":   {"href": "/api/v1/tasks/42"},
    "update": {"href": "/api/v1/tasks/42", "method": "PATCH"},
    "delete": {"href": "/api/v1/tasks/42", "method": "DELETE"},
    "owner":  {"href": "/api/v1/users/7"}
  }
}

Le modèle de maturité de Richardson distingue quatre niveaux :

NiveauCaractéristiqueExemple
0Un seul endpoint, style RPCPOST /api avec une action dans le corps
1Ressources identifiées par des URIs/tasks/42
2Verbes HTTP + codes de statutGET, POST, 404
3HATEOASLiens d'actions dans la réponse

La majorité des API publiques se situent au niveau 2. HATEOAS apporte de la découvrabilité mais complexifie le client et reste peu utilisé en pratique.

7.5. Bonnes pratiques de conception REST

  • Versionner l'API : /api/v1/... ou en-tête Accept: application/vnd.api.v1+json.
  • Pagination systématique des collections : limit/offset ou curseur (cursor), avec métadonnées.
  • Filtrage, tri, recherche via query params : ?status=open&sort=-created_at&q=urgent.
  • Sparse fieldsets si nécessaire : ?fields=id,title,done.
  • Codes de statut corrects et erreurs normalisées.
  • Idempotence des écritures sensibles via Idempotency-Key.
  • Cache : ETag, Cache-Control, Last-Modified.
  • Sécurité : HTTPS, authn/authz, validation, rate limiting.
  • Documentation OpenAPI à jour et exemples réalistes.
  • Compatibilité : ajouter des champs est non cassant ; en supprimer ou renommer est cassant.

9.4. Une API CRUD complète avec FastAPI

L'exemple ci-dessous implémente l'API Tâches en mémoire (remplaçable par une base de données). Il illustre les routes, les paramètres, Pydantic, les codes de statut, les erreurs et la documentation automatique.

from datetime import date
from typing import Annotated

from fastapi import FastAPI, HTTPException, Path, Query, status
from pydantic import BaseModel, Field, ConfigDict

app = FastAPI(
    title="API Tâches",
    version="1.0.0",
    description="API de démonstration pour la veille API/REST",
)

# ---------- Schémas Pydantic ----------
class TaskBase(BaseModel):
    title: str = Field(min_length=1, max_length=200, examples=["Réviser HTTP"])
    due_date: date | None = None

class TaskCreate(TaskBase):
    pass

class TaskUpdate(BaseModel):
    title: str | None = Field(default=None, min_length=1, max_length=200)
    done: bool | None = None
    due_date: date | None = None

class Task(TaskBase):
    model_config = ConfigDict(from_attributes=True)
    id: int
    done: bool = False
    created_at: date

# ---------- "Base de données" en mémoire ----------
tasks: dict[int, Task] = {}
next_id = 1

# ---------- Routes ----------
@app.get("/api/v1/tasks", response_model=list[Task], tags=["tasks"])
def list_tasks(
    done: Annotated[bool | None, Query(description="Filtrer par état")] = None,
    limit: Annotated[int, Query(ge=1, le=100)] = 20,
    offset: Annotated[int, Query(ge=0)] = 0,
):
    items = list(tasks.values())
    if done is not None:
        items = [t for t in items if t.done == done]
    return items[offset:offset + limit]

@app.get("/api/v1/tasks/{task_id}", response_model=Task, tags=["tasks"])
def get_task(task_id: Annotated[int, Path(ge=1)]):
    if task_id not in tasks:
        raise HTTPException(status_code=404, detail="Tâche introuvable")
    return tasks[task_id]

@app.post("/api/v1/tasks", response_model=Task,
          status_code=status.HTTP_201_CREATED, tags=["tasks"])
def create_task(payload: TaskCreate):
    global next_id
    task = Task(id=next_id, created_at=date.today(), **payload.model_dump())
    tasks[next_id] = task
    next_id += 1
    return task

@app.patch("/api/v1/tasks/{task_id}", response_model=Task, tags=["tasks"])
def update_task(task_id: int, payload: TaskUpdate):
    if task_id not in tasks:
        raise HTTPException(status_code=404, detail="Tâche introuvable")
    current = tasks[task_id]
    updated = current.model_copy(update=payload.model_dump(exclude_unset=True))
    tasks[task_id] = updated
    return updated

@app.delete("/api/v1/tasks/{task_id}", status_code=status.HTTP_204_NO_CONTENT, tags=["tasks"])
def delete_task(task_id: int):
    if task_id not in tasks:
        raise HTTPException(status_code=404, detail="Tâche introuvable")
    del tasks[task_id]

9.6. Dépendances (injection)

Une dépendance est une fonction exécutée avant l'endpoint, dont le résultat est injecté. Elle sert à factoriser l'authentification, l'accès à la base, la pagination ou les permissions.

from fastapi import Depends, Header

def get_db():
    db = SessionLocal()
    try:
        yield db          # code exécuté après la réponse
    finally:
        db.close()

def get_current_user(
    authorization: Annotated[str, Header()],
    db: Session = Depends(get_db),
) -> User:
    token = authorization.removeprefix("Bearer ").strip()
    user = decode_and_verify(token, db)
    if not user:
        raise HTTPException(401, "Token invalide")
    return user

@app.get("/api/v1/me")
def read_me(user: User = Depends(get_current_user)):
    return user

Les dépendances se composent, se surchargent dans les tests (app.dependency_overrides) et peuvent être asynchrones.

XProgrammation synchrone et asynchrone

Une API passe l'essentiel de son temps à attendre : réseau, base de données, fichiers, services externes. Le mode d'exécution détermine sa capacité à servir plusieurs requêtes sans bloquer.

10.1. Programmation synchrone

Le code s'exécute ligne après ligne. Un appel bloquant (lecture disque, requête SQL, appel HTTP) immobilise le thread jusqu'à la fin de l'opération. Pour traiter plusieurs requêtes, le serveur utilise plusieurs threads ou processus.

import requests

def get_weather(city: str) -> dict:
    # Bloque le thread jusqu'à la réponse (plusieurs centaines de ms)
    response = requests.get(f"https://api.meteo.example/{city}", timeout=5)
    response.raise_for_status()
    return response.json()

def handler():
    data = get_weather("Lyon")   # rien d'autre ne s'exécute ici
    return data

Avantages : simplicité, compatibilité avec la plupart des bibliothèques, débogage facile.
Inconvénients : consommation de threads, mauvaise utilisation des I/O, saturation sous forte concurrence.

10.2. Programmation asynchrone

Le code utilise une boucle d'événements (event loop). Quand une opération d'I/O est lancée avec await, le contrôle est rendu à la boucle qui peut exécuter d'autres tâches ; le résultat est repris lorsque l'opération est terminée. Un seul thread peut ainsi gérer des milliers de connexions en attente.

import asyncio
import httpx

async def get_weather(city: str) -> dict:
    # Non bloquant : la boucle peut servir d'autres requêtes pendant l'attente
    async with httpx.AsyncClient(timeout=5) as client:
        response = await client.get(f"https://api.meteo.example/{city}")
        response.raise_for_status()
        return response.json()

async def handler():
    # Trois appels exécutés en parallèle
    lyon, paris, nice = await asyncio.gather(
        get_weather("Lyon"),
        get_weather("Paris"),
        get_weather("Nice"),
    )
    return {"lyon": lyon, "paris": paris, "nice": nice}

Avantages : excellent pour les I/O et les connexions nombreuses, faible empreinte mémoire, latence réduite.
Inconvénients : complexité, écosystème de bibliothèques inégal, risque de bloquer la boucle avec du code synchrone ou du CPU intensif.

10.3. Comparaison entre synchrone et asynchrone

CritèreSynchroneAsynchrone

10.4. Async dans FastAPI

FastAPI est construit sur ASGI et supporte les deux styles :

  • async def : exécuté dans la boucle d'événements. Utiliser des bibliothèques async (httpx, asyncpg, motor).
  • def : exécuté dans un threadpool géré par AnyIO. Adapté aux bibliothèques synchrones (requests, psycopg2).
@app.get("/sync")
def sync_endpoint():
    # OK : FastAPI l'exécute dans un threadpool
    return requests.get("https://api.exemple.com/data").json()

@app.get("/async")
async def async_endpoint():
    # OK : bibliothèque async
    async with httpx.AsyncClient() as client:
        r = await client.get("https://api.exemple.com/data")
    return r.json()

@app.get("/bad")
async def bad_endpoint():
    # DANGER : requests est bloquant et gèle la boucle d'événements
    return requests.get("https://api.exemple.com/data").json()
Les pièges de l'async
  • Appeler une bibliothèque bloquante dans async def : toute l'API ralentit.
  • Faire du calcul lourd (image, cryptographie, ML) dans la boucle : déporter dans un processus.
  • Oublier await : la coroutine n'est jamais exécutée.
  • Créer une session/base par requête sans la fermer : fuite de ressources.
  • Mélanger sync et async sans comprendre le threadpool : comportements imprévisibles.
Règle de décision simple

I/O et forte concurrence → async def + bibliothèques async. Bibliothèque uniquement synchrone ou code CPU → def (threadpool) ou processus séparé. En cas de doute, mesurer avec un test de charge (Locust, k6).

XISécurité des API : authentification et autorisation

Sécuriser une API consiste d'abord à répondre à deux questions : qui appelle (authentification) et a-t-il le droit de le faire (autorisation).

11.1. Principes fondamentaux

  • Confidentialité, intégrité, disponibilité (CIA) : protéger les données, garantir qu'elles ne sont pas altérées, maintenir le service.
  • Moindre privilège : chaque utilisateur, service ou token ne reçoit que les droits nécessaires.
  • Défense en profondeur : plusieurs couches (TLS, auth, validation, rate limiting, logs, WAF).
  • Zéro confiance : ne jamais faire confiance à l'entrée client, même interne.
  • Échec sécurisé : en cas d'erreur, refuser l'accès plutôt que l'accorder.
  • Secrets hors du code : variables d'environnement, coffre-fort (Vault), rotation.
  • Journalisation et audit : tracer les accès sensibles sans stocker de secrets.
  • Validation systématique : types, tailles, formats, listes blanches.

11.3. OAuth2

OAuth2 (RFC 6749) est un cadre d'autorisation déléguée : une application (client) obtient un accès limité à une ressource au nom d'un utilisateur, sans connaître son mot de passe. OpenID Connect (OIDC) ajoute l'authentification et le profil via un jeton d'identité (ID token).

Les rôles

  • Resource Owner : l'utilisateur qui possède les données.
  • Client : l'application qui demande l'accès.
  • Authorization Server : délivre les tokens après authentification et consentement.
  • Resource Server : l'API qui protège les ressources et valide les tokens.

Les flows principaux

FlowContextePrincipe
Authorization Code + PKCESPA, mobile, webRedirection, code échangé contre token ; PKCE protège le code.
Client CredentialsServeur à serveurLe client s'authentifie directement, pas d'utilisateur.
Device CodeTV, CLI, objets connectésL'utilisateur valide sur un autre appareil.
Refresh TokenTous les flows avec utilisateurRenouveler l'access token sans redemander le mot de passe.
Implicit / PasswordDépréciésÀ éviter (fuite de token, stockage du mot de passe).

Exemple de flow Authorization Code + PKCE

  1. Le client génère un code_verifier aléatoire et son empreinte code_challenge.
  2. Redirection vers l'Authorization Server avec client_id, redirect_uri, scope, state, code_challenge.
  3. L'utilisateur s'authentifie et consent ; le serveur redirige avec un code.
  4. Le client échange le code + code_verifier contre un access_token (et souvent un refresh_token).
  5. Le client appelle l'API avec Authorization: Bearer <access_token>.
  6. L'API valide la signature, l'expiration, l'audience, l'émetteur et les scopes.

11.4. JSON Web Token (JWT)

Un JWT (RFC 7519) est un jeton compact et signé, composé de trois parties encodées en Base64URL et séparées par des points :

header.payload.signature

# Header
{"alg": "RS256", "typ": "JWT", "kid": "2026-10"}

# Payload (claims)
{
  "iss": "https://auth.exemple.com",
  "sub": "user-42",
  "aud": "api-taches",
  "exp": 1793520000,
  "iat": 1793516400,
  "scope": "tasks:read tasks:write",
  "role": "user",
  "jti": "8f14e45f-..."
}

Signature : garantit l'intégrité et l'authenticité, pas la confidentialité. Le payload est lisible par tous : ne jamais y mettre de secret, de mot de passe ou de donnée personnelle sensible.

AlgorithmeTypeUsage
HS256Symétrique (secret partagé)Un seul émetteur et un seul vérificateur ; simple mais secret partagé.
RS256 / RS512Asymétrique (RSA)Émetteur signe avec la clé privée, API vérifie avec la clé publique (JWKS).
ES256Asymétrique (ECDSA)Signatures plus courtes, performances intéressantes.

Validation d'un JWT côté API

  1. Récupérer le token dans l'en-tête Authorization: Bearer ....
  2. Vérifier la signature avec la clé appropriée (JWKS pour les clés asymétriques).
  3. Vérifier exp (expiration), nbf (pas avant), iss (émetteur) et aud (audience).
  4. Vérifier les scopes/rôles requis pour l'opération.
  5. Refuser les algorithmes non attendus (jamais none), limiter le clock skew.
# Exemple avec PyJWT
import jwt
from jwt import InvalidTokenError

PUBLIC_KEY = load_public_key()

def decode_token(token: str) -> dict:
    try:
        return jwt.decode(
            token,
            PUBLIC_KEY,
            algorithms=["RS256"],
            audience="api-taches",
            issuer="https://auth.exemple.com",
            options={"require": ["exp", "iat", "iss", "aud"]},
        )
    except InvalidTokenError as exc:
        raise HTTPException(status_code=401, detail="Token invalide") from exc

Bonnes pratiques JWT

  • Access token court (5 à 15 min) et refresh token plus long, avec rotation et révocation.
  • Stocker les tokens de manière sûre : cookies HttpOnly + Secure + SameSite pour le web, stockage sécurisé natif pour mobile.
  • Ne pas stocker de données sensibles dans le payload.
  • Valider strictement alg, iss, aud, exp ; utiliser les JWKS et le kid.
  • Prévoir une liste de révocation ou un jti pour les tokens critiques.
  • Utiliser HTTPS partout ; jamais de token dans l'URL (fuite par logs et referer).
Vulnérabilités JWT classiques
  • Algorithme none accepté : toujours imposer une liste d'algorithmes.
  • Confusion de clé (HS256 vérifié avec une clé publique) : séparer les types de clés.
  • Absence de vérification de l'audience : un token destiné à un autre service est accepté.
  • Expiration trop longue : un token volé reste valide des jours.
  • Stockage en localStorage : exposé au XSS ; préférer des cookies sécurisés.

11.5. Autorisation et bonnes pratiques

  • RBAC (rôles) ou ABAC (attributs) selon la granularité nécessaire.
  • Vérifier la propriété de chaque objet (BOLA) : un utilisateur ne lit que ses tâches.
  • Contrôler les fonctions sensibles (admin) séparément des objets.
  • Limiter le débit (rate limiting) et la taille des requêtes.
  • Configurer CORS avec une liste blanche d'origines.
  • Ajouter les en-têtes de sécurité : Strict-Transport-Security, X-Content-Type-Options, Content-Security-Policy (pour les interfaces).
  • Journaliser les événements d'authentification et les accès sensibles.
  • Faire des revues de sécurité et des tests d'intrusion ; scanner les dépendances (pip-audit).

✓Conclusion et aide-mémoire

Une API réussie est un produit : un contrat clair, un protocole bien utilisé, une architecture adaptée, une sécurité sérieuse et un déploiement reproductible.

Synthèse en dix points

  1. Une API est un contrat d'interopérabilité, pas seulement du code.
  2. REST = ressources + méthodes HTTP + représentations + sans état + cache.
  3. Choisir le style (REST, GraphQL, gRPC, SOAP) selon le besoin, pas par mode.
  4. L'architecture doit suivre l'organisation et l'échelle, pas l'inverse.
  5. HTTP fournit la sémantique : méthodes, codes, en-têtes, cache.
  6. Des erreurs normalisées (RFC 9457) réduisent le coût d'intégration.
  7. OpenAPI + Swagger UI rendent l'API découvrable et testable.
  8. FastAPI combine types, validation, documentation et performance.
  9. OAuth2/JWT : authentifier, autoriser, valider, expirer, révoquer.
  10. Docker + Coolify/Dokku/CapRover rendent le déploiement reproductible.

Checklist finale du projet

  • Contrat OpenAPI versionné et documentation à jour.
  • Validation des entrées et erreurs normalisées.
  • Authentification et autorisation testées (BOLA, admin, scopes).
  • Rate limiting, quotas et limites de taille.
  • Logs corrélés, métriques et health check.
  • Tests unitaires et d'intégration, CI verte.
  • Dockerfile reproductible et variables d'environnement documentées.
  • HTTPS, en-têtes de sécurité, secrets protégés.
  • Sauvegardes et procédure de restauration.
  • Guide de démarrage pour les développeurs.
Mot de la fin

La théorie (HTTP, REST, architectures) donne le vocabulaire ; FastAPI donne les moyens ; la sécurité et le déploiement donnent la crédibilité. C'est la combinaison des trois qui transforme un exercice en API utilisable en production.
